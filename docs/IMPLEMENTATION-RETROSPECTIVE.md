# 尔意堂品牌官网：实现复盘与同类项目知识库

版本：正式交付复盘版 1.0  
基线日期：2026-08-29  
适用对象：项目负责人、设计与开发人员、WordPress实施人员、运维人员及后续接手的AI

## 1. 文档定位

这不是一份以品牌介绍为主的案例稿，而是一份可以复用的工程知识库。项目背景和需求只保留理解方案所必需的部分，重点回答：网站如何实现、为什么这样实现、如何从原型稳定迁移到WordPress、上线过程中哪里容易出错，以及下一次怎样更快、更稳地完成类似项目。

## 2. 项目简述

尔意堂官网是一个强调传统文化感、真实内容维护和长期可运营性的中医馆品牌网站。公开页面包括首页、品牌介绍、联系我们、文章列表/分类及文章详情。主要动态内容包括文章、医师、资质、广告、Banner、联系方式和页面固定内容。

项目的核心难点并不在页面数量，而在四组约束同时存在：

1. 视觉要有明确品牌气质，不能成为通用模板；
2. 医疗、资质和非遗相关信息不能由开发者或AI补写事实；
3. 客户没有持续操作服务器和代码的能力，日常维护必须集中在WordPress后台；
4. 静态视觉稿、WordPress实现、生产数据库、媒体库和服务器配置必须最终收敛成可恢复的单一正式版本。

## 3. 最终实现方案

### 3.1 总体架构

项目采用传统WordPress一体式架构，而不是Headless WordPress：

```text
浏览器
  ↓ HTTPS / Nginx
WordPress 7.1 + PHP 8.3
  ├─ eryitang 主题：结构、模板、样式、交互和静态视觉资源
  ├─ eryitang-core 插件：内容类型、后台字段、设置页、短代码、SEO/GEO
  ├─ MySQL 8.0：文章、分类、媒体记录、业务配置和固定内容
  └─ wp-content/uploads：正式上传媒体
```

选择一体式WordPress的原因是：项目没有复杂前后端应用状态，不需要独立前端部署；客户的主要任务是内容维护；服务端渲染更直接，有利于SEO；同时减少跨域、鉴权、构建发布和双系统运维成本。

### 3.2 主题与插件职责划分

主题负责“长什么样、页面如何组成”：

- 页面模板、模板部件和公共页头页脚；
- CSS设计令牌、响应式规则和动效；
- 页面固定结构与默认视觉资源；
- 前台JavaScript交互。

功能插件负责“数据是什么、后台如何维护”：

- 医师、资质等自定义内容类型；
- 文章推荐、首页展示、相关文章等元数据；
- 基础信息、页面图片、广告、链接等设置页；
- 页面固定内容及分区保存、回退和图片比例校验；
- 动态查询与短代码；
- meta description、Open Graph、Twitter Card、JSON-LD、面包屑和`llms.txt`。

这条边界非常重要。把业务字段写进主题，会在换主题时丢失内容能力；把大量视觉结构写进插件，则让样式维护变得困难。

### 3.3 内容模型

- 固定独立页面：首页、品牌介绍、联系我们、文章资讯；
- 文章：WordPress原生文章，使用一级和二级分类组织；
- 医师：独立内容类型，维护照片、职称、方向、坐诊和排序；
- 资质：独立内容类型，维护证书图片、名称、说明和排序；
- 公共配置：电话、地址、营业时间、备案、地图和公共链接；
- 页面媒体：四类Banner、联系图片和二维码；
- 展示配置：广告、推荐文章、首页资讯、疗法卡片跳转；
- 固定内容：原本写在模板里的品牌文字、模块图片和装饰背景。

“结构冻结、内容后台化”是项目后期稳定的关键。客户可以更新内容，但不能从后台破坏模块顺序、CSS、容器比例和响应式规则。

## 4. 实施流程复盘

### 4.1 需求先转成不可擅改的约束

项目初期不要只记录“做五个页面”，还要形成决策清单。例如是否需要搜索、哪些是独立页面、内容如何分类、电话如何展示、移动端是否有底栏、哪些事实必须由客户提供。决策一旦确认，应进入项目规则文件，AI和开发者每次工作前都能读取。

经验：具体页面需求会变，边界和决策更值得固化。没有边界，后续每次优化都可能重新设计一次网站。

### 4.2 先用静态原型解决视觉，再迁移WordPress

项目先完成五类页面的静态视觉与交互基线，验证信息层级、间距、图片比例、动效和响应式，再迁移WordPress模板。这样比一开始就在WordPress后台和动态查询中同时调视觉更高效。

但静态原型只应是阶段工具。迁移完成后，WordPress主题、插件、数据库和媒体库才是运行事实源。项目中后期曾出现静态稿、本地WordPress和生产站三套口径并存，说明必须明确“当前事实源”并停止无必要的双向同步。

### 4.3 建立公共组件和设计令牌

公共页头、页脚、按钮、Banner、广告、焦点状态、颜色、间距和字体规则应先收敛。项目实践证明，页面级重复覆盖会导致：

- 修一个页面时其他页面继续保留旧规则；
- 桌面端看似正常，平板或手机出现冲突；
- 发布后浏览器混合缓存新旧CSS，问题难以定位；
- AI根据单页截图增加更多补丁，使技术债继续扩大。

正确方式是优先修改公共令牌和公共组件；页面特殊规则必须使用明确的页面作用域。

### 4.4 从静态页面迁移到动态模板

迁移不是复制HTML后把文字替换为PHP。应分四层完成：

1. 保留已确认的DOM结构和CSS类；
2. 把公共组件抽成模板部件；
3. 把文章、分类、医师、资质等替换为动态查询；
4. 把客户真正需要维护的字段开放到后台。

迁移时应先建立“静态元素—WordPress数据源—后台入口—默认值—空状态”的映射表。每个模块都要回答：没有图片、没有链接、没有内容或只录入一部分时，页面如何表现。

### 4.5 后台能力按风险分层

项目最终形成三层维护能力：

- 高频低风险：文章、图片、医师、资质、电话、地址；
- 中频中风险：广告、跳转链接、推荐关系和SEO字段；
- 低频高风险：页面固定内容、背景图和公共标识。

高风险字段通过独立菜单、分区保存、字数提示、图片比例校验、二次确认和“上一次配置”回退降低误操作概率。这个设计比简单地“全部做成可编辑字段”更适合非技术客户。

### 4.6 移动端和跨浏览器收口

移动适配不是最后统一缩小字号，而是逐类处理：导航、Banner、内容网格、图片裁切、按钮触控区、长文字、侧栏重排、底部备案和动效降级。项目固定检查1440px、768px和390px，并补充iOS Safari、Android Chrome及微信内置浏览器真机验证。

真实设备验证不能完全由无头浏览器替代。无头浏览器适合检查断图、溢出、控制台错误和结构缺失；真机更容易暴露Safari字体度量、浏览器工具栏高度、触摸滚动及微信WebView差异。

### 4.7 上线和生产收口

最终环境为Nginx、PHP 8.3、MySQL 8.0。迁移时排除Studio的SQLite数据库和相关drop-in，只迁移经过验证的MySQL兼容数据、主题、功能插件和媒体文件。上线后完成：

- 主域名与历史域名301归一；
- HTTPS和HTTP/2；
- XML-RPC阻断及基础安全响应头；
- 图片WebP压缩和中文文件名资源修复；
- WordPress时区、固定链接、索引开关和备案信息；
- Sitemap、meta、社交分享标签、Schema和`llms.txt`；
- 桌面与手机正式站回归。

## 5. 核心工作流

### 5.1 内容发布流

```text
核实事实与授权
→ 准备文字和规定比例图片
→ WordPress后台录入
→ 预览与分类/链接核对
→ 发布
→ PC与手机正式站检查
→ 记录变更
```

医疗效果、医师资质、非遗级别、证书编号和患者案例不得由AI自动补全。开发者只提供字段和空状态，事实由客户确认。

### 5.2 代码发布流

```text
从Git正式基线创建分支
→ 本地修改主题或插件
→ PHP语法与静态检查
→ 桌面/平板/手机回归
→ 高风险任务建立恢复点
→ 上传服务器临时目录
→ 服务器PHP 8.3检查与哈希核对
→ 覆盖正式相对路径
→ 正式站回归
→ 提交Git并更新记录
```

生产环境不应成为唯一修改位置。紧急修复如果必须在服务器完成，也必须立即回写Git，否则下一次部署会覆盖修复。

### 5.3 恢复流

```text
GitHub main
→ 校验MANIFEST
→ 空服务器安装固定版本WordPress
→ 导入主题/插件/媒体
→ 导入正式内容数据库
→ 创建新管理员与新秘密
→ 配置Nginx/TLS
→ 自动检查
→ 人工双端验收
→ DNS切换
```

源码备份不等于完整恢复备份。只有代码、数据库、媒体、环境版本、服务器配置和恢复说明同时存在，并完成过恢复演练，才能称为可恢复交付。

## 6. 主要问题与踩坑

### 6.1 仓库分裂和Git元数据混乱

项目曾同时存在外层开发仓库、内层静态站GitHub仓库和生产服务器文件。外层没有远端，内层`main`仍是旧静态版本，生产WordPress更新没有进入GitHub。

根因：早期把GitHub视为静态页面展示仓库，后期架构转向WordPress后没有立即重建发布边界。

改进：项目架构确认后立即定义唯一仓库；生产发布必须关联提交；数据库与媒体使用独立备份策略；交付时从生产事实源反向校验，不相信旧分支名称和旧文档描述。

### 6.2 过程快照和QA产物膨胀

大量页面截图、回退目录、渲染产物和临时文件占用超过1.5GB，正式文件反而不易识别。

根因：每轮都建立完整目录副本，缺少保留周期和产物目录规范。

改进：普通代码变更依赖Git；只有数据库迁移、核心升级和批量媒体替换建立完整恢复点；QA产物集中到临时目录并设置交付清理清单；阶段结束只保留最终报告和关键证据摘要。

### 6.3 静态原型与WordPress双源

部分阶段静态V2和WordPress都被描述为“当前版本”，导致修改是否需要双向同步不清晰。

改进：原型确认后冻结为设计参考；运行实现完成后，主题/插件/生产数据是唯一事实源。只有客户明确需要独立静态演示包时才维护第二份产物。

### 6.4 Studio版本与SQLite兼容回归

WordPress Studio 1.18.0出现SQLite启动问题，而1.17.0可运行。若把工具故障误判为数据库损坏，容易采取重建站点或覆盖数据库等高风险操作。

改进：先做只读完整性检查、版本回退和副本验证；本地SQLite只用于开发，不复制到MySQL生产；迁移数据使用明确的MySQL兼容导出。

### 6.5 Linux中文资源路径404

本地环境对文件名大小写和中文路径更宽容，Linux/Nginx生产环境暴露了背景图404。

改进：生产静态资源统一使用小写英文、数字和连字符；部署前执行引用路径存在性检查；区分CSS背景图与内容图片，避免同一视觉重复请求。

### 6.6 浏览器字体度量导致重叠

固定高度的竖排标题在系统文字缩放、替代字体或浏览器最小字号下可能超过容器并覆盖按钮。常规机器上无法稳定复现。

改进：文本容器使用`min-height`而不是固定`height`；按钮不参与压缩；测试网页缩放、系统字体放大和替代字体；布局不依赖某一字体的精确像素高度。

### 6.7 自动化测试误报

平板双栏布局中，不同列元素共享纵坐标，被一维顺序检测误判为重叠。

改进：视觉结构检测使用二维矩形相交，而不是只比较Y轴；失败项必须结合截图和DOM几何复核，不能直接根据一个规则修改页面。

### 6.8 图片体积与缓存

原始证照和Banner较大，同名覆盖又容易命中旧缓存。生产优化后48个WebP把约77.26MB源图压缩到约4.29MB，移动端图片传输下降约79%—87%。

改进：上传前裁切压缩；大图最长边限制；新版本尽量使用新英文文件名；CSS和媒体引用同步更新；性能验收记录实际传输量而不是只看源文件大小。

### 6.9 生产发布与恢复点尺度

每次小改都做整站备份会拖慢交付，但完全不备份又无法承受高风险操作。

改进：按风险分级。普通CSS或单文件修复依赖Git和定点回退；数据库迁移、核心升级、批量媒体替换、架构调整必须创建数据库+代码+配置恢复点，并至少验证清单和可读性。

## 7. 做得好的地方

1. **视觉先定稿再动态化**：降低了WordPress阶段同时调数据和视觉的复杂度。
2. **公共组件治理**：页头、页脚、Banner、按钮和设计令牌逐步收敛，减少页面级补丁。
3. **主题与业务插件分层**：结构样式与业务数据职责清晰，便于未来维护。
4. **客户后台能力渐进开放**：不是简单地把所有模板字段暴露，而是按风险增加提示、校验、分区保存和回退。
5. **事实边界明确**：没有用AI虚构医师资质、疗效、案例授权或公安备案号。
6. **生产验证量化**：使用HTTP状态、断图、横向溢出、DOM缺失、图片传输量和多视口结果作为证据。
7. **性能优化有闭环**：不仅压缩图片，还处理引用、重复加载、HTTP/2和生产回归。
8. **SEO/GEO做在公共层**：通过插件统一生成meta、社交标签、Schema和`llms.txt`，避免逐页补丁。
9. **最终从生产反向建立恢复基线**：避免把未同步的本地副本误当成交付版本。

## 8. 可以提前改进的地方

- 在开发第一周建立唯一仓库、目录规范和分支策略；
- 在原型批准时明确“原型冻结、WordPress成为运行事实源”的切换点；
- 建立素材台账，记录来源、授权、用途、比例、最终文件名和是否已上线；
- 将每轮完整目录备份改为Git提交、数据库定时备份和少量里程碑快照；
- 提前设计后台内容模型，减少后期从模板文字再迁移为可配置字段；
- 上线前就准备生产环境差异检查：PHP版本、数据库、文件名大小写、路径编码和缓存；
- 把恢复演练作为交付定义的一部分，而不是上线后的补充任务；
- 文档分为“当前事实”“操作手册”“历史台账”三类，历史描述不得继续出现在当前入口。

## 9. 同类项目标准SOP

### 阶段A：立项与边界

- 明确业务目标、页面范围、维护角色和上线环境；
- 列出事实敏感字段及提供责任人；
- 建立唯一Git仓库、目录规范、决策记录和完成定义；
- 确认哪些内容后台化，哪些结构冻结。

完成门槛：页面清单、内容模型、不可擅改决策和素材责任表均已确认。

### 阶段B：信息架构与原型

- 先完成公共页头页脚和设计令牌；
- 制作代表性页面，再扩展同类页面；
- 同时验证1440px和390px，不等桌面全部完成后再补手机；
- 建立图片比例、空状态和链接行为规范。

完成门槛：所有页面结构、公共组件和响应式方向通过确认。

### 阶段C：CMS实现

- 建立字段映射表；
- 先做内容类型和公共设置，再迁移模板；
- 保持原型DOM和CSS类，避免迁移时重新设计；
- 为无数据、无图、无链接、未授权内容准备安全状态；
- 对高风险后台字段添加校验和回退。

完成门槛：客户无需代码即可完成约定的日常维护，且不能从后台破坏页面结构。

### 阶段D：内容与合规

- 文字、图片、资质、案例逐项核实来源；
- 图片统一英文文件名、比例和压缩标准；
- SEO描述基于真实内容，不堆砌或虚构；
- 未确认字段保持为空或安全占位，不由AI补写。

完成门槛：正式站不存在测试账号、草稿、无授权案例和虚构事实。

### 阶段E：生产迁移

- 冻结发布候选；
- 建立生产前恢复点；
- 检查PHP、MySQL、文件权限、路径大小写和扩展；
- 导入数据库、媒体、主题和插件；
- 配置HTTPS、跳转、安全头、缓存和日志；
- 完成多视口、真机、SEO、性能和后台回归。

完成门槛：主域名可访问、跳转唯一、HTTPS正常、关键页面200、无断图和横向溢出，后台维护路径可用。

### 阶段F：交付与恢复

- 从生产事实源生成源码、数据库和媒体恢复包；
- 剥离账号、密码、会话、私钥和证书秘密；
- 写明环境版本、恢复步骤和差异；
- 在隔离环境执行一次恢复演练；
- 清理本地草稿、QA产物、重复快照和嵌套仓库；
- 将干净基线推送GitHub `main`。

完成门槛：不是“文件已上传”，而是“从备份能恢复并通过验收”。

AI执行任务前必须先判断修改属于主题、插件、数据库内容、媒体还是服务器配置；不能根据一张截图在多个页面追加互相覆盖的CSS；不能把旧静态原型当成当前正式源码。

## 11. 长期维护注意事项

- TLS证书、WordPress核心、PHP和MySQL版本会变化，应单独建立到期和升级提醒；
- 核心升级前验证主题、插件和数据库兼容性，不在生产站直接试错；
- 定期导出数据库和媒体，并存放在服务器之外；
- GitHub备份更新后至少校验SHA-256和恢复脚本；
- 客户后台修改不自动进入Git，需按周期刷新数据库/媒体恢复基线；
- 真实医师、资质、案例和品牌权威内容变化时，同步检查页面、Schema、SEO描述和`llms.txt`；
- 不要删除仍被数据库引用的媒体；先替换、验证，再清理；
- 发生故障时先冻结和取证，再决定回退代码、数据库、媒体或配置，避免不同时间点混合恢复。

## 12. 最终结论

这类品牌官网真正的工程价值不只是把页面做出来，而是把视觉、内容模型、客户维护能力、事实合规、生产发布和灾难恢复连接成一个闭环。最值得复用的原则有三条：

1. 原型可以多轮，正式运行事实源只能有一个；
2. 后台可编辑不等于无限开放，必须按风险设计维护能力；
3. 只有经过验证、能够重新初始化站点的备份，才算完成交付。
